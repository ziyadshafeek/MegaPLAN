PRACTICAL GUIDE

How to write code with ChatGPT without losing control of the project

The best results come from treating ChatGPT as a coding collaborator with a written project contract—not as a one-message code generator.

1. Start with the job, not the framework

Describe what the software must do, who uses it, what must be automated, what should stay local, what may run on a server, and how success will be tested.

Build a browser extension that works on YouTube. Core job: capture the current video URL and transcript when available. Also: open NotebookLM and AI Studio with a prepared workflow. No account, no analytics, no exposed API keys. Tests: manifest validation, JS syntax, message passing, error states.

2. Give the AI a durable project context

A long chat is not a reliable source of truth. Keep a MASTER_CONTEXT.md or AGENTS.md in the repository with architecture, commands, constraints, current state, known bugs and definition of done.

Good handoff: “Read the master context first. Inspect the existing files. Do not replace working modules unnecessarily. Add one feature, test it, then update the context.”

3. Ask for small vertical slices

Instead of asking for a thousand lines at once, ask for one complete flow: input → processing → output → error handling → test. Then move to the next flow.

4. Make the AI prove the code works

Ask for deterministic checks after every build: JSON parsing, syntax checks, unit tests, smoke tests and—when the environment supports it—real browser interaction.

Before saying “done”: 1. run the tests 2. inspect the exact failure output 3. fix the root cause 4. rerun the failing test 5. test the happy path and at least one invalid input 6. state what was actually verified

5. Separate product logic from integrations

For example, our study extension treats YouTube, NotebookLM, AI Studio and OCR providers as integrations around a small internal workflow engine. This makes provider changes much less destructive.

6. Use prompts that preserve completeness

For exam material, a useful prompt is not merely “summarise this.” The prompt should define what “complete” means.

Convert this source into detailed study notes in source order. Cover every important point, definition, list, number, mechanism, example and warning. Do not invent information or silently omit sections. Use concise bullets, clear headings and mnemonics only where they improve recall.

7. Long PDFs: split before asking for slide decks

A 200-page document is easier to manage when split into numbered sections. FreeToolForge StudyBridge can prepare 20 sections and attach a matching prompt to each one. This lets you make several smaller decks and merge them afterward.

8. The real secret: keep the repository boring

Use predictable folders, small modules, explicit tests and a written status file. Future agents should be able to continue without reconstructing the entire conversation.
